# Deployment

Status: **live since 2026-10-03.** The environment is created and the first release is deployed. The
page is a placeholder; the dashboard and API are not built yet.

- URL: <https://18-197-138-116.sslip.io> (health check: `/healthz`, shows the deployed commit)
- Release: `git push origin main:deploy`
- Run locally: `cp .env.example .env && docker compose up -d --build`, then open `http://localhost`

This replaces the earlier Oracle / Hugging Face / Modal proposal.

Goal: judges open one public HTTPS URL and everything works. No team laptops, no venue Wi-Fi.

## Decisions

| Topic | Decision |
|---|---|
| Host | One AWS EC2 instance, `t3.large` (2 vCPU, 8 GB RAM), region `eu-central-1` (Frankfurt) |
| Budget | Under $5 in total. The instance runs for less than 24 hours and is destroyed after judging |
| LLM | An external model through our own API key, instead of Ollama, for now. Any provider is acceptable; the choice is made later and is one config value. No GPU on our side |
| Not used | Team laptops, AWS ECS, Oracle Cloud, Hugging Face Spaces, Modal |
| Packaging | Docker Compose on the instance |
| HTTPS | Caddy in front, hostname `<elastic-ip>.sslip.io` (no domain purchase) |
| Infrastructure | Terraform, applied once by the AWS account owner from their own machine |
| Deploys | GitHub Actions, on every push to the `deploy` branch. Pushing to `main` does **not** deploy |
| Web framework | FastAPI + uvicorn |
| Agent | OpenCode runs inside the app container, with our adapter loaded |
| Frontend hosting | Not decided yet, and not needed for the deployment. Default: static files served from the same container |
| API contract | Decided later. The infrastructure is built first and does not depend on it |
| Demo data | Regenerated by one command on every deploy |
| Team access | The team tests locally and deploys by moving `deploy` forward. Nobody but the owner gets AWS or instance access |

### LLM decision

We use **paid LLM APIs** through our own key (team decision). No LLM is provided by the organizers.

- The **agent we protect** and the **semantic guard** both call hosted API models.
- API spend is itself governed: the budget controls in the policy cap tokens and cost per session and per day.
- The judge-run test suite must work **without any API key**. It uses a stub; the real API is used
  only for the live demo.
- Which provider and models is decided later. Any provider is acceptable.

### Cost

On-demand prices checked through the AWS pricing API on 2026-10-03:

| Item | Price | 24 hours |
|---|---|---|
| `t3.large` | $0.096 / hour | $2.30 |
| Public IPv4 address and 20 GB gp3 disk (estimate) | about $0.20 / day | $0.20 |

## Stack

| Part | Choice |
|---|---|
| Gateway + API | FastAPI + uvicorn; serves the API and the dashboard from one process and one origin |
| Dashboard | Default: plain HTML/CSS/JS in `/static`, live feed over SSE, no CDN assets. Not final (see Frontend and backend) |
| Semantic guard | Fast, cheap API model (e.g. Claude Haiku 4.5) as a prompt-injection judge, returning a score. No model weights to host; its latency shows in the pipeline trace |
| Agent | OpenCode v2.0.22 with the `adapters/opencode` plugin, started by the backend inside the container |
| LLM (the agent we protect) | Stronger API model with tool calling (e.g. Claude Sonnet 5.5), configured in OpenCode's provider settings. Provider and model can be swapped without code changes |
| Storage | SQLite files (audit store, consumer ledger, synthetic bank database) on a Docker volume |

In the repository: `web/main.py` (FastAPI: `/healthz`, the config and run APIs, and the static mounts),
`static/html/` (pages: the dashboard and `/opencode-wrapper/`), `static/css/`, `static/js/`, `Dockerfile`, `compose.yaml`, `Caddyfile`, `.env.example`, `infra/main.tf` and
`.github/workflows/deploy.yml`.

## Frontend and backend

```text
browser ──HTTPS──> Caddy ──> app container
                              ├─ FastAPI: serves /static (the frontend) and /api/v1/* (JSON + SSE)
                              ├─ gateway (loopback only)  <── adapter ── OpenCode ──> external LLM
                              └─ SQLite files on the data volume
```

- **Where the frontend lives (default, not final):** plain HTML/CSS/JS in a `static/` folder in this
  repository, inside the same Docker image as the backend. No separate frontend host and no build
  step. It ships with the same deploy.
- **How it talks to the backend:** same origin, so no CORS setup.
  - Requests and actions (send a prompt, load metrics, read or save config, run tests): JSON over HTTP
    under `/api/v1/...`.
  - Live feed and streaming test results: Server-Sent Events, read in the browser with `EventSource`.
- **What the browser never reaches:** the gateway, the SQLite files, OpenCode and the LLM API key. The
  gateway keeps listening on `127.0.0.1` inside the container; only FastAPI is exposed through Caddy.
- **The API contract is not fixed yet.** The infrastructure only needs FastAPI to answer `/healthz`
  and serve `/static`. Endpoints are added later without touching the deployment.

### Session API and the OpenCode wrapper page (implemented)

The jury page is at `/opencode-wrapper`. It is a chat with an OpenCode agent that runs with our plugin.
It shows the agent's replies and the gateway's decision for every tool call. Scenarios and the test
suite live elsewhere; this page has neither.

Opening the page starts a **session** (`web/sessions.py`): one long-lived OpenCode server
(`opencode serve`) plus one control gateway (`intercept.local --catalog-all`). Messages are sent to
the running server with `opencode run --server`, so only the session start pays the start-up cost.
Measured on the instance with `gpt-4.1-mini`: about 1-3 s to start a session, then about 2-4 s per message.

- The agent gets a generic prompt and is offered every registered tool, including the ones policy
  forbids, so blocks are visible. It remembers earlier messages until a new session is started.
- All sessions start from one synthetic bank, generated once when the app starts. The gateway gives
  each session its own copy, so one visitor's writes do not show up in another's session.
- Each session is assigned to `APP-0001`, because the gateway needs one case per session, and has the
  policy's tool-call budget (30 calls).

| Endpoint | Purpose |
|---|---|
| `GET /api/v1/info` | Model and assigned application |
| `POST /api/v1/sessions` | Start a session. Returns `201` and a `session_id` once it is ready |
| `POST /api/v1/sessions/{id}/messages` | Send `{"prompt": "..."}`. Returns the agent's `reply`, plus all `events` and `findings` so far |
| `GET /api/v1/sessions/{id}/events` | Sanitized events (each with the gateway's `reason_code`) and findings; polled while the agent works |
| `DELETE /api/v1/sessions/{id}` | Stop the session's processes |

- Limits: `MAX_SESSIONS` (6) live sessions, where the least recently used idle one makes room for a new
  one; sessions idle for `SESSION_IDLE_S` (900 s) are closed; `RUN_TIMEOUT_S` (120 s) per message;
  `RUNS_DAILY_CAP` (500) messages per day. Over a limit the API answers `429`.
- Sessions live in memory. A deploy or restart ends them; the page then starts a new one.
- Not available: raw tool arguments and results (events are sanitized by design). Messages are passed
  to the agent but not stored by the web layer.
- Tests (`tests/test_web_sessions.py`) use a fake backend, so they need no OpenCode and no API key.

### Guard vs agent

- The **semantic guard is a security control**. It runs on every request that reaches it, after the
  deterministic checks, and its latency shows in the pipeline trace. A hard deny skips it and saves the API call.
- The **agent LLM is the system being protected**. It answers the chat console and drives the agent
  demo. It never runs as a blocking security check.
- Always stream agent responses and cap `max_tokens`. Set request timeouts. On provider errors the
  guard fails closed.

### Frontend choices that can wait

How the frontend is built and hosted does not affect the instance, Terraform, Caddy, the `deploy`
branch or the deploy workflow. It can be decided after the infrastructure is up.

| Later choice | What changes |
|---|---|
| Plain files or a framework (React, Vue) | Only the `Dockerfile`: a framework adds one build step. The output is still static files |
| Served from the same container (default) | Nothing |
| Hosted elsewhere (for example Vercel or S3) | A second deploy pipeline, and CORS settings on the backend so the browser may call it |

Plain static files are enough for every feature in [ai-brainstorm-ui.md](ai-brainstorm-ui.md): the
page's JavaScript calls the API for data and actions, and reads live updates over SSE. Charts or a
config editor with line-level errors would use a library file copied into `static/`.

### OpenCode in the container

The chat console drives the real OpenCode agent, not only the built-in simulation agent.

- The image installs Node and OpenCode pinned to v2.0.22, next to Python and `uv`.
- The backend starts OpenCode non-interactively for a chat message (`opencode run`), in a workspace
  whose `opencode.json` loads `adapters/opencode` and denies shell and file-edit permissions.
- `INTERCEPT_TOKEN` is generated at container start and passed to both the gateway and OpenCode. It
  never leaves the container.
- Each OpenCode session is bound to a Task Contract by the backend through the gateway's operator
  endpoint before the first tool call. Unbound sessions are denied by the gateway.

Not proven yet: the repository has verified that real OpenCode loads the adapter and completes the
handshake (interactive mode, no prompt sent). A full non-interactive prompt through the adapter, with
tool calls, has not been run. The built-in simulation agent (`simulation.agent`) stays available as the
fallback behind the same chat endpoint.

## Where each secret lives

No AWS credential ever leaves the owner's machine. GitHub never receives one, because Terraform runs
locally and the deploy workflow only uses SSH.

| Secret | Lives in | Who can read it |
|---|---|---|
| AWS access keys | Owner's machine (`~/.aws`) only | Owner |
| Terraform state (`infra/*.tfstate`) | Owner's machine, git-ignored | Owner |
| Deploy SSH private key | Generated on the owner's machine; stored as GitHub Actions secret `DEPLOY_SSH_KEY` | Owner. GitHub hides secret values from collaborators |
| Instance address | GitHub Actions secret `DEPLOY_HOST` (also public: it is the judges' URL) | Everyone |
| Instance SSH host key | GitHub Actions secret `DEPLOY_KNOWN_HOSTS`, so the workflow only connects to the real instance | Not sensitive |
| LLM API key | `/opt/app/.env` on the instance, written once by the owner over SSH | Owner |
| Admin token (policy changes, data reset) | `/opt/app/.env` on the instance | Owner, and whoever the owner shares it with |

Rules that keep it this way:

1. `.gitignore` gets `infra/.terraform/`, `*.tfstate*`, `*.tfvars` and `.env` **before** the first Terraform run.
2. Terraform receives only the SSH **public** key. The private key is created with `ssh-keygen`, not by
   Terraform, so it never appears in the state file.
3. Nothing in the repository contains the AWS account ID, access keys or the LLM key. Local development
   uses a personal `.env` copied from a committed `.env.example` with empty values.
4. The app must not log secrets, because failure logs are printed in the workflow run (and are public
   if the repository is public).

Known limit: anyone who can push to the repository can change or add a workflow, and that workflow could
read `DEPLOY_SSH_KEY`. That key opens the one instance, not the AWS account. We accept this inside the team.

## Deployment plan

Two separate parts: Terraform creates the machine once, GitHub Actions ships the code on every push
to the `deploy` branch.

```text
OWNER, once                         ANY TEAM MEMBER, per release
terraform apply                     work lands on main (tests run, nothing deploys)
        │                                │
        ▼                                ▼
EC2 + Elastic IP + firewall         git push origin main:deploy
        │                                │
        ▼                                ▼
cloud-init installs Docker          deploy workflow: tests, then SSH to the instance
and clones the deploy branch        git pull + docker compose up -d --build
        │                                │
        ▼                                ▼
owner writes .env over SSH          health check; on failure, print container logs
```

### Why Terraform

- The whole environment is one small file, and `terraform destroy` removes every billable resource in
  one command. That is the cost control.
- A hand-written CLI script would be about as short, but has no reliable teardown.
- ECS, a container registry and a load balancer are not needed for a single instance.

### Step 1: Container files (repository root) — any team member

1. `Dockerfile`: Python image with `uv sync --locked`, plus Node and OpenCode v2.0.22; starts uvicorn.
2. `compose.yaml` with two services:
   - `app`: the gateway and dashboard, with a named volume for the SQLite files and `env_file: .env`.
   - `caddy`: reverse proxy on ports 80 and 443, automatic certificate for the hostname in `SITE_HOST`.
3. `restart: unless-stopped` on both services, so a reboot does not take the demo down.
4. A minimal FastAPI app: `/healthz` for the deploy check and a `static/` mount. No other endpoints are needed yet.
5. `.env.example` with every variable name and no values.

Check: `docker compose up` works on a laptop and the dashboard opens on `http://localhost`.

### Step 2: Terraform (`infra/`) — owner only

One `main.tf` creating:

1. A security group: ports 80 and 443 open to everyone; port 22 open with key-only login.
2. A key pair from the deploy SSH public key.
3. The EC2 instance: Ubuntu 24.04, `t3.large`, 20 GB gp3 disk, `credit_specification { cpu_credits = "standard" }`.
4. An Elastic IP attached to the instance, so the URL never changes.
5. `user_data` (cloud-init) that installs Docker and clones the `deploy` branch to `/opt/app`.
6. Outputs: the public IP and the final URL.

Optional: an AWS Budgets alert at $5, as a safety net if the instance is forgotten.

Then the owner, over SSH, once:

1. Writes `/opt/app/.env` (LLM API key, admin token, `SITE_HOST`).
2. Runs `docker compose up -d` and opens the URL.

### Step 3: GitHub secrets — owner only

Add `DEPLOY_SSH_KEY`, `DEPLOY_HOST` and `DEPLOY_KNOWN_HOSTS` in the repository's Actions secrets.

### Step 4: Deploy workflow (`.github/workflows/deploy.yml`) — any team member

1. Trigger: a push to the `deploy` branch. Pushes to `main` and to feature branches do nothing here.
2. First job: run the test suite (`uv run pytest`). If it fails, nothing is deployed.
3. Second job: SSH to the instance and run
   `git fetch && git reset --hard origin/deploy && docker compose up -d --build`,
   then `docker compose exec -T app python data/generate.py` to regenerate the demo data.
4. Request `https://<url>/healthz`. If it does not answer, print `docker compose logs --tail 200 app`
   and fail the job. This is how the team sees cloud-only errors without instance access.
5. `concurrency` group so two pushes cannot deploy at the same time.

### How to release

`deploy` only ever moves forward to a commit that is already on `main`:

```bash
git push origin main:deploy
```

- This deploys your local `main`, so run `git pull` on `main` first. To deploy an older commit, use `git push origin <sha>:deploy`.
- Nobody commits directly to `deploy`. It is a pointer to "what is live", not a place for work.
- Roll back by pushing an earlier commit: `git push --force origin <good-sha>:deploy`.
- The commit `deploy` points at is always the version judges see.

### What a deploy does

- The instance keeps running. Only the `app` container is rebuilt and replaced; Caddy and its
  certificate stay up.
- Downtime is the few seconds of the container swap.
- The synthetic bank database is regenerated on every deploy (deterministic, seed 2026), so demo data
  always starts clean. Changes judges made to it are lost.
- The audit store on the volume is not touched, so recorded events survive. They can refer to bank
  records that the regeneration has reset.
- Anything the app holds only in memory resets.
- A build that fails leaves the old container running. A container that builds but crashes on start
  takes the site down until the next good release or a rollback; the workflow turns red.
- The URL and IP do not change.

### Step 5: Freeze and teardown — owner

- Stop releasing to `deploy` shortly before judging, so a deploy does not land mid-demo. Work on `main` can continue.
- After judging: `terraform destroy`. This removes the instance, the disk and the Elastic IP. Confirm
  in the AWS console that nothing is left, then delete the two GitHub secrets.

### Order of work

1. Minimal FastAPI app with `/healthz` and `static/` (blocks everything else).
2. `Dockerfile`, `compose.yaml`, `.env.example`; test locally.
3. `.gitignore` entries, then `infra/main.tf` and `terraform apply`; write `.env` on the instance.
4. Create the `deploy` branch, add the GitHub secrets and `deploy.yml`; release once and watch the deploy.
5. Put the URL in the slides and the QR code.

## Configuration

All environment-specific values come from the policy file and environment variables, so the same
image runs locally and on the instance:

```sh
# .env on the instance (names only; values are never committed)
SITE_HOST=<elastic-ip>.sslip.io
LLM_PROVIDER=openai
LLM_MODEL=gpt-4.1-mini
OPENAI_API_KEY=
OPENCODE_MODEL=openai/gpt-4.1-mini
ADMIN_TOKEN=
```

OpenCode reads the provider's own variable name (`OPENAI_API_KEY`), not a generic one, and takes the
model as `provider/model`.

Verified on the instance on 2026-10-04: one synthetic application run through OpenCode, the gateway
and the verifier inside the app container, ending in `VERIFIED_SUCCESS`:

```sh
docker compose exec app python -m simulation.opencode_runner APP-0001     --timeout 300 --output-dir /data/pipeline-runs
```

`--output-dir` must point outside the repository (here: the data volume). The runner's default folder
is inside the repository and is rejected by its own isolation check.

Guard settings live in the policy file (example values, not final):

```yaml
semantic_guard:
  provider: anthropic
  model: claude-haiku-4-5
  api_key_env: LLM_API_KEY
  block_threshold: 0.9
  on_error: block        # fail closed
```

## Before judging

- [ ] The public URL loads on a phone over mobile data (not venue Wi-Fi).
- [ ] The first chat answer comes back in a few seconds; check the account spend limit.
- [ ] Model swap tested: change the model setting and confirm it is picked up.
- [ ] Demo data is seeded.
- [ ] The test suite runs from a fresh clone with **no API key** (uses a stub).
- [ ] Recorded trajectory replay works without the LLM.
- [ ] If the LLM is unreachable, the chat console shows a clear "LLM offline" state and the guard checks still run.
- [ ] The last deploy workflow run is green, and `deploy` points at the commit we want judged.

## Open questions

1. Which external provider and model, and who owns the API key and its spending limit? Decided later; any provider is acceptable.
2. Is the GitHub repository public? If it is private, the instance needs a read-only deploy key to clone it.
3. Port 22 is open to the internet so GitHub's runners can reach it (key-only login). The alternative,
   AWS Systems Manager, closes the port but takes longer to set up.
4. Does OpenCode run a full prompt non-interactively with the adapter loaded? Test this early; the
   simulation agent is the fallback.
5. `sslip.io` certificates depend on Let's Encrypt rate limits for that shared domain. Fallback: plain
   HTTP on the IP, or a real domain.
