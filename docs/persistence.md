# Standalone persistence component

`persistence/` implements local evidence storage and analytics delivery. It does
not intercept agents, enforce policy, authorize approvals, reserve budgets, or
verify banking outcomes. Only trusted gateway/orchestrator code may invoke this
API or register in-process callbacks. It has no public or model-facing endpoint.
Do not expose these methods as agent tools. Identifiers and `AuditContext` must
come from the trusted orchestrator, not model arguments or correlation headers.

## Two ingestion paths

| API | Meaning of success | Appropriate use |
|---|---|---|
| `await engine.emit_action(event)` | Sanitized immutable event and all registered consumer jobs committed together to file-backed SQLite | Required intents, decisions, denies and result evidence |
| `engine.emit_action_nowait(event)` | Owned sanitized snapshot accepted into bounded memory | Optional best-effort telemetry only |
| `await engine.emit_alert(...)` / `emit_audit_action(...)` | Sanitized immutable record committed | Reporting; these do not transact a banking effect |

`PersistenceEngine` requires an explicit nonempty file path and rejects
`:memory:`. Lower-level `EventStore()` may be ephemeral for unit tests, but its
durable outbox API also rejects ephemeral storage. The default outbox capacity
is 10,000 **delivery jobs**, not 10,000 events: an event creates one job per
registered consumer, including the internal live-feed consumer. Atomic capacity
checks cover concurrent connections using the same configured limit.

Critical callers must await the commit before backend dispatch and stop on an
exception, including `AuditBackpressureError`. A critical append is not placed
in memory and deferred until after the effect. Cancellation/timeout after a
commit starts can leave committed evidence: reconcile by the original event ID;
never interpret cancellation as proof of rollback or repeat a business effect.
`emit_action(timeout=...)` bounds lifecycle-lock acquisition, not an in-flight
SQLite commit. SQLite has a five-second busy timeout.

SQLite uses WAL and `synchronous=FULL`. These guarantees depend on the local
filesystem honoring synchronization. Tests cover process exit after acceptance,
not power loss, filesystem corruption, or every possible mid-commit crash.

## Evidence and privacy

Persistence projects arbitrary payloads onto the structured allowlist in
`persistence/privacy.py` before writing or fanout. It omits names, raw input,
attachments, prompts, result blobs, nested objects, errors, auditor free-text
reasons and proposed modifications. It retains opaque resource references,
known status codes and finite nonnegative measurements. Invalid identifiers,
status codes, verdicts or measurements fail validation. `sanitized_fields` is
generated by this boundary; a caller's label is not proof of sanitization.
Exception logs contain fixed messages, and DLQ errors contain a fixed code.

Token syntax and signature checks cannot establish that a value is an opaque
identifier: e.g. a person's name without spaces resembles a token. The trusted
issuer must supply opaque IDs and reason codes; never put personal data or
secrets into an ID field. This component is not a comprehensive DLP detector.
Raw dataclass `to_dict()` / `to_json()` are interchange helpers, not sanitized
export APIs. Export records through the store, never raw caller objects.

`AuditContext` supports contract/run/action/principal references, policy hash,
feed version, approval/intervention references, usage, semantic-model identity,
receipt and verification status. Missing values remain `None`; storage does
not invent a binding or prove that a supplied one is authentic. A supplied run
ID requires a gateway-assigned event index. `(run_id, action_index)` is unique;
intent/result events have separate indices but can share the same action ID.
`get_run_events()` orders by this index. Case/session/trace views order by
normalized UTC timestamp with insertion order as a stable tie breaker; they
are chronological views, not a substitute for the trusted run ordering.

An identical sanitized record retry is idempotent. Conflicting ID reuse or
index reuse raises `ConflictingRecordError`, and a batch rolls back atomically.
Intent and result must have different event IDs; evidence is append-only until
explicit operator-authorized retention deletion. Retry comparison concerns the
sanitized record, not omitted raw payloads.

## Analytics and live feeds

Attach an async analytics callback with
`await engine.register_consumer("metrics", callback)`. Consumer names persist.
On restart, reattach the same name to resume outstanding jobs. An unattached
consumer's jobs remain pending and count toward capacity. Register before
emitting events, or request `replay=True` to enqueue retained history on a
consumer's first registration. Replay is atomic and capacity checked.

Deliveries are at least once. Leases serialize active claims across connections;
expired leases can be reclaimed and stale acknowledgments cannot delete another
claim. Consumer success acknowledges its job. Exceptions/timeouts trigger
jittered bounded exponential retry; after the initial attempt plus three
retries, the job atomically moves to the sanitized DLQ. Defaults are a five-second
callback timeout and a 35-second lease. Crash recovery of a claimed job waits
for lease expiry. Attempts are charged when claimed, so repeated process crashes
without acknowledgment also exhaust the retry limit. Callbacks must cooperate
with cancellation.

Consumers must deduplicate event IDs in their own durable transaction, including
the crash window after processing and before acknowledgment. They must never
perform business effects. Registered callbacks are trusted Python code; storage
does not sandbox arbitrary callback I/O. Cross-consumer processing order is not
guaranteed, and retries can deliver an older event after a newer one; trajectory
consumers must use run indices and detect gaps.

`subscribe_live_feed()` creates volatile bounded queues. Overflow/filter failure
increments telemetry; evidence remains queryable for reconnect/replay. Queue
delivery is not consumer-processing acknowledgment. Live feeds cannot serve as
durable semantic supervision or outcome verification.

`worker.flush()` waits for committed volatile batches and deliveries to attached
consumers, and raises on timeout. It does not wait for unattached consumers;
inspect `pending_deliveries` to see those jobs. Shutdown refuses new emits,
drains, and then closes the connection. On drain timeout it raises and keeps the
worker/store alive so an operator can restore the cause and retry `stop()`.

## Retention, access and checks

`get_stats()` exposes counts, latency, backlog, volatile rejections, live-feed
drops/filter errors and worker error class. `prune_before(UTC_timestamp)` applies
an explicit trusted retention cutoff and preserves events with pending jobs.
There is no automatic scheduler or public export/admin endpoint. Deployment must
choose retention limits, authorize pruning/exports, restrict filesystem access,
and monitor file growth. Pending capacity alone does not bound the database.
Reads/exports also project legacy records onto the allowlist, but old bytes from
the earlier raw-payload implementation are not erased or migrated on disk. Use
a fresh disposable store for synthetic demos.

No runtime dependency was added: SQLite/asyncio are Python standard library
components; pytest remains a development dependency. Run the synthetic checks:

```sh
uv run --locked --offline pytest
```

The persistence test suite includes:
- `tests/test_persistence.py`: Core event store, outbox, and delivery operations.
- `tests/test_persistence_failures.py`: Failure modes, corruption, and retry backoff.
- `tests/test_persistence_schema.py`: Schema migrations, metadata, and constraints.
- `tests/test_persistence_writer.py`: Run binding and sequential action indexing.
- `tests/test_persistence_business.py`: Banking effect receipts and outbox replication.
- `tests/test_persistence_lifecycle.py`: Engine lifecycle, consumer pause/resume/retire, and derived alerts.
- `tests/test_persistence_maintenance.py`: Maintenance reports, pruning, quota enforcement, and backup/restore.
- `tests/test_persistence_reader.py`: Scoped reader, keyset pagination, export quotas, and run reports.
- `tests/test_persistence_integration.py`: Multiprocess crash boundary recovery matrix.

## Persistence Demo CLI

Run the integrated persistence demonstration across all failure and recovery scenarios:

```sh
# 1. Clean happy path: authorized action, bank commit, receipt replication, verification
uv run python -m persistence.demo --scenario clean

# 2. Audit store unavailable: action blocked before bank effect is attempted
uv run python -m persistence.demo --scenario audit-unavailable

# 3. Process crash after bank commit: effect committed, replicator recovers and imports audit event
uv run python -m persistence.demo --scenario crash-after-bank

# 4. Corrupted external state: bank modified without receipt, verifier detects postcondition failure
uv run python -m persistence.demo --scenario wrong-state
```
